Source data: `data/t20s_json/` — 5,700 match JSON files + `README.txt`.
Generated by `scripts/explore_schema.py` (re-run it to regenerate the numbers below).

## 1. Inventory

| Item | Value |
|---|---|
| File formats present | JSON only (`.json`, data_version `1.2.0`) |
| Match files | 5,700 |
| Non-match files | `README.txt` (Cricsheet's match index / changelog text, 415 KB, one line per match) |
| Registry files (`people.csv`, `names.csv`) | **None present** — player IDs live only in each match file's `info.registry.people` |

**No format decision needed** — this download (`t20s_json.zip`) already contains only the JSON format, not YAML/CSV/CSV2. Cricsheet's JSON is the right source of truth in general (typed, nested, versioned, actively maintained) — this just confirms the local folder matches that recommendation.

Per `README.txt`: this archive is restricted to T20 matches, and 158 matches involving Afghanistan (men's team, or played in the Afghanistan Premier League) are **withheld** by Cricsheet policy — not a bug in your pipeline, just an upstream exclusion to be aware of.

Confirmed empirically (see §3): every file has `match_type == "T20"`, `team_type == "international"`, `balls_per_over == 6`, `data_version == "1.2.0"`. This is a clean, single-format, single-match-type, international-only T20 dataset — no club/league T20 (e.g. IPL) is present, and no Test/ODI cross-contamination.

## 3. Full-corpus scan results (all 5,700 files)

### 3.1 `info.outcome` shapes

| Shape (sorted keys present) | Count | Meaning |
|---|---|---|
| `by, winner` | 5,344 | normal decisive result — `by.runs` (2,814) or `by.wickets` (2,718)‡ |
| `by, method, winner` | 188 | decisive result reached via a method — always `method: "D/L"` in this bucket |
| `result` | 114 | `result: "no result"` (113) or `"tie"` with no further resolution (1, i.e. tied and not sent to a super over — match `1142504`) |
| `eliminator, result` | 46 | `result: "tie"` + `eliminator: <team>` — tie resolved by a super over |
| `method, winner` | 4 | e.g. `{"winner": "Ghana", "method": "Awarded"}` — match awarded without a `by` margin (walkover/forfeit-style ruling) |
| `method, result` | 2 | e.g. `{"result": "tie", "method": "D/L"}` — tied under D/L, no super over |
| `bowl_out, result` | 2 | e.g. `{"bowl_out": "India", "result": "tie"}` — old-style bowl-out decider (pre-super-over era) instead of `eliminator` |

‡ No match has `by.innings` (0 occurrences) — expected, since innings-margin wins only occur in multi-innings formats (Tests), not T20.

`outcome.result` values: `no result` = 113, `tie` = 51 (= 46 resolved by `eliminator` + 2 by `bowl_out` + 2 by D/L method + 1 left as a bare, fully unresolved tie).
`outcome.method` values: `D/L` = 190, `Awarded` = 4.
`outcome.eliminator` present on 46 matches. `outcome.bowl_out` present on 2 matches (very old, pre-2009 super-over-rule matches).

### 3.2 Innings counts

| `len(innings)` | Matches | Interpretation |
|---|---|---|
| 1 | 84 | match ended before a 2nd innings started — abandonments/no-results |
| 2 | 5,570 | normal completed (or 2nd-innings-interrupted) match |
| 4 | 45 | 2 main innings + 2 super-over innings |
| 8 | 1 | 2 main innings + 6 super-over innings — a match that needed **3 successive tied super overs** to resolve |

46 matches have ≥1 innings flagged `super_over: true` (96 super-over innings total = 45×2 + 1×6), matching the `eliminator`-decided count (46) exactly — i.e. every super-over match in this corpus has an `eliminator` outcome (none of the old `bowl_out` matches in this file set went through a `super_over`-flagged innings; bowl-outs predate the super-over mechanic and are recorded as separate, non-`innings`-shaped resolutions).

### 3.3 `innings[1].target` (2nd innings, non-super-over)

Of 5,616 matches with a 2nd (non-super-over) innings:
- **5,589** have a `target` object.
- **27** do not — these are matches where the 2nd innings started but was curtailed too early for a target to be computed/recorded (partial-innings no-results).
- **190** have `target.runs != first_innings_total + 1`, i.e. a rain/method-revised target rather than a plain chase. Of these, **most but not all carry `outcome.method == "D/L"`** — a handful (e.g. match `1138202`, `1177484`, `1183527`) show a revised target with `outcome_method: None`, meaning the target was adjusted (overs reduced, presumably before the chase began) but the final result didn't end up needing D/L to be invoked as the deciding method. **This is a real edge case for modeling: a mismatched target is not a reliable proxy for "this was a D/L match."**

### 3.4 Distributions

- **match_type**: 100% `T20` (uniform — this file set is T20-only by construction).
- **gender**: male 3,539 (62.1%) / female 2,161 (37.9%).
- **team_type**: 100% `international` (uniform — no club competitions in this download).
- **balls_per_over**: 100% = 6.
- **year** (from `dates[0]`): heavily skewed toward recent years — growth from single digits/year pre-2010 to 900+/year in 2024–2026, reflecting T20I's explosive recent growth (associate nations, women's game, more bilateral series) plus Cricsheet's improving historical coverage.

### 3.5 Venue naming inconsistencies

453 distinct raw `venue` strings. A simple "same name, with/without a city suffix" heuristic (grouping by the text before the first comma) surfaces **40+ suspected duplicate groups**, e.g.:

- `"Eden Gardens"` vs `"Eden Gardens, Kolkata"`
- `"Bay Oval"` vs `"Bay Oval, Mount Maunganui"`
- `"Edgbaston"` vs `"Edgbaston, Birmingham"`
- `"Arun Jaitley Stadium"` vs `"Arun Jaitley Stadium, Delhi"`
- **`"County Ground"` alone is genuinely ambiguous** — it appears bare *and* with 6 different city suffixes (Bristol, Chelmsford, Derby, Hove, New Road/Worcester, Northampton), so the bare form can't even be safely assumed to mean one specific ground.
- Similar pairs for Allan Border Field, Amini Park, Barabati Stadium, Barsapara, Basin Reserve, Bellerive Oval, Boland Park, Brabourne Stadium, Buffalo Park, Coolidge Cricket Ground, Gaddafi Stadium, Gymkhana Club Ground (2 different cities: Dar-es-Salaam and Nairobi — a *false-positive* duplicate risk if you naively merge by prefix), Hagley Oval, Hazelaarweg, Holkar Cricket Stadium, and more (full list in script output).

This is a genuine data quality issue for any venue-level feature (e.g. average par score per ground): the same physical ground is sometimes recorded with a city suffix and sometimes without, and naive string-prefix matching would also wrongly merge grounds that share a generic name (e.g. two different "Gymkhana Club Ground"s in different countries).

### 3.6 Player identity

- `info.registry.people` is present in **100%** of files (0 missing) and does give a stable per-player hex ID that (mostly) persists across matches/files.
- **Name collisions exist in both directions**, so `registry.people` should be trusted over raw name strings:
  - **69 display names map to more than one ID** — i.e. two distinct real players share an identical short name within the corpus (e.g. `"Rashid Khan"` → 4 different IDs, `"Muhammad Usman"` → 4 different IDs, `"Mandeep Singh"`, `"A Mishra"`, `"Shahid Afridi"`, etc.). Cricsheet's own convention disambiguates some of these with a `" (2)"`/`" (3)"` suffix in the name field, but the collisions above are cases where **the bare, unsuffixed name is still ambiguous** across IDs.
  - **17 IDs map to more than one display name** — the same real player recorded under different names, mostly from (a) marriage/name changes (e.g. `KH Brunt` ↔ `KH Sciver-Brunt`, `NR Sciver` ↔ `NR Sciver-Brunt`, `L Winfield` ↔ `L Winfield-Hill`), or (b) a switch between initials-style and full-first-name style (e.g. `P Agnihotri` ↔ `Pratik Agnihotri`, `S Singh` ↔ `Sukhdeep Singh`), or (c) a disambiguating suffix being added retroactively to the same ID (`Mohammad Nawaz` ↔ `Mohammad Nawaz (3)`).
- **Practical implication**: for any player-level feature (batting average, strike rate history, etc.), join on `registry.people` ID, never on the raw name string.

## 5. Recommended filters for a 2nd-innings forecasting dataset

These are proposals for you to confirm (see open questions below):

- **Keep**: `match_type == "T20"` (already uniform here), both genders (model separately or add `gender` as a feature — see open question), all years.
- **Drop matches with `len(innings) < 2`** (issue #1) — no 2nd innings to forecast.
- **Drop/exclude super-over innings from the 2nd-innings dataset** (issue #2) — restrict to `innings[0]` and `innings[1]` only, ignore any further innings entirely; a super over is a fundamentally different (fixed 6-ball, all-out-vs-target) mini-game, not a regular 2nd innings.
- **Drop `no result` (113) and `Awarded` (4) matches** (issues #6, #7) — no meaningful chase was completed, nothing to forecast against.
- **Keep ties, but treat carefully**: a tied 2nd innings *did* complete a real chase (final score = target − 1, by definition) — these are valid training examples for "runs scored in 2nd innings," just not for "did they win" if you also model win probability.
- **Keep D/L-affected matches, but treat as a distinct regime**: 190 matches have a revised target. Recommend adding a flag (`is_target_revised` = target.runs != first_innings_total+1) and/or `outcome_method` as a feature/segment, rather than dropping them outright — they're a meaningful chunk (3.3%) and rain-affected run-rates behave differently. Whether to fully exclude them from a first-pass model is your call.
- **Canonicalize venue** before any venue-level features: prefer the venue string that includes the city suffix where the same base name appears both with and without one; treat `"Gymkhana Club Ground"` (Nairobi vs Dar-es-Salaam) as genuinely distinct rather than merging by prefix. A `(venue, city)` composite key is safer than `venue` alone.
- **Join all player-level fields on `registry.people` ID**, never on raw name, given the collision/drift issues (#10, #11).
- **Decide how to handle `absent_hurt`, `penalty_runs`, `miscounted_overs`** (issues #12–14) — rare enough (≤2%) to plausibly ignore for v1, but they can locally distort a specific innings' ball count or wickets-in-hand.

## 6. Open questions for you

1. **Ties**: should the bare unresolved tie (1 match), `bowl_out`-decided ties (2, pre-2009), and D/L-decided ties (2) be kept in the training set, excluded, or bucketed separately from `eliminator` ties? -- Keep with a flag
2. **D/L / method-revised matches (190, 3.3%)**: fully exclude, keep with a flag/feature, or model separately from "clean" chases? -- Keep with a flag
3. **Gender**: pool male and female matches into one model (with `gender` as a feature), or build separate models? Run-rate/scoring dynamics likely differ meaningfully between the two. -- Keep with a flag
4. **Associate nations / small-sample teams**: the year distribution shows huge recent growth, largely driven by newer/associate teams (e.g. Rwanda, Botswana, Kenya, Serbia, Bulgaria in the sample). Should these be kept (more data, more variance) or filtered to a fixed tier of teams/boards for a cleaner signal? -- keep them
5. **Time horizon**: given the heavy skew toward 2022–2026 (very little pre-2015 data), do you want to weight/filter by recency, or use the full 2005–2026 span as-is? -- use them as is
6. **Venue canonicalization**: do you want a manual mapping table (~40 known groups) or a fuzzy/geocoded approach (e.g. resolve via city + country) given `city` is missing on 3.1% of matches? -- We'll use a fuzzy approach
7. **`Afghanistan`-related withheld matches**: 158 matches are withheld upstream by Cricsheet policy (not recoverable from this download) — just flagging so the resulting team-level dataset for Afghanistan will be incomplete, in case that matters for your team coverage.
